# 随机数确定性与 SL / NoSL：Spire2Lab 工程笔记

日期：2026-11-19。研究对象是项目当前《杀戮尖塔2》v0.111.1，不将一代机制或其他补丁当作实测结论。
本轮只读资料/元数据，并尝试离线RNG调用；没有原版游戏动作、训练或房间回滚验收。

## 已确认的用户要求

- 铁甲战士、A0、完整自主通关；12月28日课程最终硬指标，第一幕仅作中间门。
- NoSL：不读档重试、不回滚重选、不重复真实动作择优，失败纳入统计。
- 最低NoSL门：10局至少1局完整通关；理想目标约60%，不把小样本成绩当长期胜率保证。
- SL：仅当前房间可回滚，禁止回到之前房间；用户允许无限次，不设次数上限。
- 用户已确认先前“SL不回滚”是笔误，实际指NoSL。两组数据仍须分开统计，NoSL为主。
- 训练可使用SL；次数不限不等于已决定运行无限长时间，耗时/停止和未完成局统计仍待明确。

## 1. 固定种子到底固定什么

Mega Crit工程师在官方RNG说明中指出：STS2使用伪随机数；同一种子初始化的同一生成器会产生
同一数字序列。一局有多条从run seed派生的随机流，分别影响抽牌、奖励、事件等；公告还说明了
v0.107.1的生成器更换。这里只将其作为开发者对机制的说明，不把公告等同当前构建的全量验证。
[官方Major Update #2的RNG说明](https://store.steampowered.com/news/posts/?enddate=1781830684&feed=steam_community_announcements)

工程上应表达为：相同版本/规则、相同完整状态（含各RNG当前位置）、相同动作和相同调用条件，
才应得到可复现的后续游戏结果。一个seed不足以描述一局进行到中途的状态。

“固定随机序列”不等于“每一张牌的结果独立于玩家操作、在开局已全部写死”。
动作可能改变所使用的流、调用次数、调用参数、候选集合以及其他游戏状态。
某些随机量可能提前生成，另一些在动作发生时生成；不能把整个游戏当作一张固定结果表。

示意（非游戏实测数值）：某流后续值为r1、r2、r3。
- 路径A：第一次随机效果使用r1，第二次使用r2。
- 路径B：先触发一次同流随机效果，再执行A中的效果，则可能从r2开始对应。
- 若额外效果使用另一条流，它未必推进原来的流。
- 相同随机数映射到不同候选集合，也可能产生不同对象。
并不是每张牌/每个操作都会推进同一条流；具体调用点需要逐项核对。

## 2. 当前DLL中实际核对到的内容

引用为用户上传的v0.111.1/cc1f9462，sts2 SHA：
`3fb1fa1bf0249087b706a5d0f062a60579e2f5b08df4ee477ddd6f2607f654d5`。
下面来自PE元数据，不是从wiki推测，也未执行相应游戏流程：

- `RunRngSet`含多个RNG对象，公开`Seed`为UInt64；旧冻结DLL为UInt32。
- `RunRngType`区分Shuffle、CombatCardGeneration、CombatCardSelection、CombatTargets、
  MonsterAi、UnknownMapPoint等用途，不能假设全游戏共享一个计数器。
- `PlayerRngSet`有Rewards、Shops、Transformations及序列化/恢复接口。
- `Rng`有Next系列、Shuffle、ToSerializable、LoadFromSerializable及保存对象构造函数。
- `SerializableRng`含counter及四个UInt64状态字段state0、state1、state2、state3。
- `MegaRandom`含四个内部状态字段、Splitmix64、Reinitialise和FillSerializableState。

元数据证明接口/状态结构存在，不能单独证明房间存档完整保存了所有状态，或每种卡牌都能精确重现。
官方v0.111.1说明也提及内部种子扩大；同页后面的v0.113.0修复不能套用于当前v0.111.1。

`evangambit/sts2@37e4264115546b6ac640d54aab3d7e2ac6983d2d`，目标v0.107.1。
它可帮助定位旧实现，不能替代v0.111.1实机参考。

## 3. 对SL的意义

如果确实完整恢复了房间入口状态，并重放同一组动作、同一随机调用，应重现同一结果。
因此SL应搜索不同决策路径；在确定性成立的条件下，重复完全相同路径不是重新抽一次独立运气。

回滚需要恢复所有影响结果的状态：房间入口、玩家/敌人、牌堆顺序、资源、效果计数器和RNG等。
只恢复血量、手牌，或仅用初始seed重新初始化RNG，都不足以保证回到原来的房间入口。
同房间的分支必须共享同一合法入口；不重新抽seed，不回退之前房间，不修改原版资源。

无限次SL不保证100%通关：当前入口可能没有可获胜路径，搜索也可能循环或无法穷尽；
此前房间的选择已经提交，不能通过当前房间回滚撤销。系统必须识别重复分支并记录实际成本。
这是工程推论，不是已证明任何特定seed必败或已实现完整搜索器。

## 4. 对NoSL与训练的意义

- 环境的潜在确定性不等于策略可以读取未来。真实seed、RNG内部状态、隐藏牌序仍留在评测器/
  私有审计侧，不作为NoSL策略输入。
- NoSL中独立模拟器按公开信息进行规划，与回滚真实游戏是不同操作；不能用真实快照或同局
  SL探索到的未来结果伪装成公开信息。原信息边界保持不变。
- 训练可以从同一房间做多个SL分支，但它们是相关数据；不能把同一局的不同分支随机拆入
  训练集和最终评估集，再称为独立泛化成绩。
- 冻结模型、版本和评估清单。相同开局做SL/NoSL配对比较是可研究的方案，必须隔离跨协议
  记忆及测试信息，不能先看SL结果再给NoSL作答；此具体评估方案尚未冻结。
- SL统计除通关外还应记录房间回滚次数、分支数、耗时及未完成局；无限次数许可不允许删除
  长时间未完成或失败的局来抬高胜率。如何设置观测窗口/停止条件仍待用户确认。

## 5. 下一步应验证什么（待执行，不是验收结论）

1. 真实游戏同一房间入口保存/恢复后，相同动作轨迹的公开状态是否逐步一致。
2. 改变一种明确触发随机调用的动作，验证出现的差异；区分不同流与非随机的状态差异。
3. 重开同seed但不恢复中途状态，与完整房间恢复是否不同；不可把重新开局冒充回滚。
4. 回滚边界不可跨前房间，NoSL执行入口明确拒绝任何回滚请求。
5. 诊断日志包含版本、入口/分支标识和审计状态，策略输入中不出现真实隐藏信息。

这些检查需先解决当前Windows监听与新版控制适配；现有只读探针不能执行它们。
单幕配方原为shouldSave=false，SL恢复方式需单独设计和验证，不能直接改用户重要存档。
