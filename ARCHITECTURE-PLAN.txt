Spire2Lab：三个阶段的总体规划与第一阶段执行计划
规划日期：2026-10-19
修订日期：2026-10-22；按用户要求收敛为三个阶段，原创优先。
路线版本：three-stage-v1。此版本替代此前五阶段划分，保留原有功能目标与实机验收。
仓库：https://github.com/Lidz-abel/Spire2Lab.git

目标与约束
建立可搜索、可分层决策、可高效训练的自主强化学习系统，并在真实《杀戮尖塔 2》中评估。
第一阶段交付有限范围内可信、可观察、可复现的环境；之后扩展策略、内容和训练规模。
Linux 承担模拟、搜索、策略推理、训练、日志与面板服务；低配置 Windows 运行 Steam
游戏、轻量状态/动作桥接及后续画面采集。Windows 不承担批量采样或训练。
当前采用结构化玩家可见观测和实验面板；后续接入原版画面。

三个阶段总览
阶段 1：可信实验平台。自主平台核心、统一环境接口、实时决策面板、轨迹复现、
         Windows 实机执行、有限范围原版对照，以及可接入搜索和训练的接口。
         交付可运行、可检查、可复现且声明证据范围的环境版本。
阶段 2：搜索与分层决策。自研预算搜索、可见历史约束的未知状态采样、上层目标与
         下层行动执行，逐步从单场战斗扩展到单幕决策。
         交付策略、可重放的搜索/层级记录、固定预算下的基线对比和消融。
阶段 3：高效训练与原版评测。策略/价值学习、并行采样、批量推理、搜索数据训练，
         扩展已验证的整局内容，并在真实游戏中报告表现与计算成本。
         交付模型、训练配方、复现实验、效率/泛化/迁移评测及原版画面演示。

原版画面是一条贯穿后两阶段的交付线：阶段 1 保证观测与动作能关联，阶段 2 接入
决策边界截图，阶段 3 完成截图/可选低帧率视频同步展示。图像展示与纯视觉策略分开。
纯视觉策略可另行研究，当前三个阶段的必要目标仍允许结构化玩家可见观测。

原创优先的实施调整（2026-10-22）
平台协议、控制、可视化、评测与后续搜索/分层/训练核心优先自行设计实现。
通用库继续使用。当前依赖中的 Python 绑定、内容数据、Mod 基础及战斗引擎
逐项隔离，独立实现达到原版对照和功能要求后切换；来源记录见 CODE-PROVENANCE.md。
本轮确定开发原则和迁移顺序，尚未替换当前后端；第一阶段仍要求有限范围实机验收。
全游戏规则重写不是新增的第一阶段完成条件，新增实现与方法创新分别记录和验证。
第一阶段必须明确本项目核心与上游后端的边界、来源和替换接口；独立绑定、最小
Mod 与有限战斗引擎按 O-02 至 O-04 推进。通过实机验收才切换，新引擎重新验收。
当前第一阶段参考引擎允许作为已标注的过渡依赖；不能据此声称已完成独立引擎。

第一阶段必须固定的六条接口边界
1. 观测与隐藏状态
   策略只获得玩家可见信息、历史记录和合法动作。未知抽牌顺序、随机数内部状态、
   未公开敌人未来动作不进入策略输入或普通面板。抽牌堆可见组成与未知顺序分别处理。
   调试和一致性校验需要的完整状态独立存储；字段缺失明确标记，不能填零冒充实测值。
   后续学习策略使用相同信息边界；评价策略时不提供比真实玩家更多的信息。
2. 语义动作与训练编码
   核心动作表达为“出哪张牌、对哪个目标、结束回合”，携带 decision_id 与请求编号。
   当前决策中的实体引用必须唯一；跨决策持久身份尚未保证，不据此关联同名卡。
   动作整数编码和神经网络张量属于可替换训练封装。扩充卡牌/阶段时升级编码版本，
   不让面板、原版适配和轨迹格式依赖固定数组位置；超出容量明确报错。
3. 决策边界与执行结果
   一步是一项玩家决策，持续到游戏完成结算并进入下一个可决策状态或终局。
   动画、轮询、网络重试不产生训练步。分开记录已建议、已提交、已确认与结果未知。
   动作请求去重；响应丢失先读取确认，禁止盲目重发。异常轨迹保留未知结果，
   不当作失败奖励或正常训练样本。人工接管单独标记，允许过滤。
4. 实际环境与搜索分支
   两种后端共用观察/动作协议，按能力声明 reset、精确快照、分支和画面支持。
   原版暂不具备任意 reset/clone；第一阶段需补齐可重复的场景初始化并验证。
   精确 snapshot/restore 服务恢复、回归测试与分支隔离。
   搜索另行使用与可见历史一致的未知状态采样，不能使用实际隐藏牌序作预知。
   当前 sample_world 是后续搜索的起点，完整历史条件化的信念模型仍需后续设计验证。
   模拟分支具有独立编号和父分支引用，不发送动作给实机，不计入真实执行轨迹。
5. 决策记录、层级与训练样本
   决策记录包含候选动作、分数含义、所选动作、策略版本、耗时和可核查的依据。
   后续追加搜索预算、访问次数/价值估计、模型检查点、上层目标及父决策编号。
   当前启发式评分不包装成概率；后续解释来自算法实际计算结果。
   原子动作轨迹作为基础事实，上层目标覆盖的多个动作另记持续步数、累计回报和
   终止条件，为跨步折扣与分层训练保留依据。
   奖励是带版本的转换规则，HP/伤害/资源变化等事实独立保存，便于重算奖励。
6. 展示、原版画面与规则
   面板只渲染统一观测和决策记录，游戏规则由原生引擎或原版游戏执行。
   卡牌、敌人、意图、数值、动作目标和决策时点必须能与原版对应。
   同一原版对局的观测、动作、截图通过 run_id/decision_id/frame_id/时间戳关联。
   后续先采集稳定决策边界的截图，再按 Windows 性能增加低帧率视频。
   原版画面展示与纯视觉智能体是两个独立里程碑；后者需要增加感知模块和独立评测。
   模拟器分支无法自动生成可信的原版截图；面板必须明确标注后端和数据来源。

第一阶段范围
铁甲战士，A0，5 张 Strike、4 张 Defend、1 张 Bash，Burning Blood，无药水，
80/80 HP、99 金币、第 2 层，三个遭遇：nibbits-weak、slimes-weak、sludge-spinner。
基线为随机合法动作和可解释启发式，完成单场战斗；暂不开展 RL 训练。
当前 config/phase1.json 定义 10 个开发种子和 10 个保留评测种子。
“2026-06-19 默认公开版本”是用户描述；最终必须采集 Steam Build ID、实际游戏
版本和 DLL 哈希。工作区的 v0.107.1 不是用户 Windows 已安装版本的证明。

第一阶段任务、顺序与交付
P1-01 版本与来源冻结（本机 v0.107.1 与构建关联已核验）
  用户运行 Connect-Windows.ps1；我们核对实际游戏版本、Steam Build ID、DLL 哈希，
  再冻结 Mod、模拟器、协议、编码和配置。版本不兼容时先解决兼容问题。
  证据：版本报告、固定依赖与可核查的构建指纹。收到报告前不宣布版本已对齐。
P1-02 自主平台核心与可替换环境接口（已有实现，边界仍需梳理）
  2026-10-23：新增 Environment 协议与显式能力拒绝，统一 step 调用，补齐模拟器
  reset；相关检查通过。边界审查仍发现 Card.native_id 与 Gym 的上游名称表耦合，
  需版本化内容词表/观测编码迁移，不能将本任务直接标为全部完成。
  由本项目维护 Observation/Action/Decision/StepResult、运行控制、数据记录和展示。
  把上游 ABI、数字 ID、数据目录和 Mod 细节限制到适配器；用能力声明表达
  observe/step/reset/snapshot/sample_world/close，原版不支持的能力必须明确拒绝。
  内容事实和采集来源分开存档；依赖迁移 O-01 至 O-04 不以改名当作独立实现。
  证据：依赖边界说明、契约验证、来源清单，以及策略/面板不读取隐藏状态的检查。
P1-03 最小实机闭环（首层真实出牌探针通过，范围内面板闭环仍待验收）
  编译桥接 -> Windows 安装 -> 读取稳定状态 -> 执行一张牌 -> 确认结算。
  然后测试结束回合、断线确认、暂停、人工接管与完整战斗；日志保留未知结果。
  证据：真实原始捕获、请求关联、规范化观测和完整执行轨迹；合成测试仅验证契约。
P1-04 可重复场景与随机性对齐（依赖 P1-03，尚未完成）
  2026-10-23：新存档自然首战为第 1 层，固定基准要求第 2 层，因此受控场景准备
  提前作为 P1-03 范围内闭环的前置工作。具体契约见 docs/SCENARIO-STAGING.md。
  最新：场景端点已编译，Python 客户端、请求契约和日志恢复的合成测试通过；
  Windows 安装和实机初始化验证尚未完成。编译/契约测试不能证明随机性已对齐。
  由我们实现受控场景准备与捕获工具，避免要求用户手动寻找 60 场相同初态。
  记录场景是游戏流程产生还是调试接口布置，核对公开初态、牌堆顺序和 RNG 来源。
  先完成一个遭遇的可重复完整对照，再扩到三种。相同数字种子不足以证明对齐；
  不得反复搜种子或改写未来状态来匹配结果。第一处差异应定位、修复并重跑。
  证据：初始化参数、重复运行轨迹、随机机制说明及所有未解决差异。
P1-05 面板与决策记录验收（已有模拟器/合成浏览器测试，实机待完成）
  显示状态、合法动作、候选评分及含义、动作建议、实际结果与后端来源。
  单步/自动/暂停/人工干预/轨迹导出/回放可用；同一实机决策与游戏对象对应。
  当前先用结构化面板，并预留 run_id/decision_id 与未来画面关联的路径。
  证据：浏览器操作结果及真实游戏步骤记录；启发式评分不充当胜率或搜索统计。
P1-06 搜索/训练接口与复现能力验收（已有基础，需整理测量证据）
  验证快照恢复、分支隔离、信息边界、合法动作掩码、终止/截断和异常样本过滤。
  验证进程隔离采样与资源释放；记录版本、初态、环境/策略种子、策略及奖励版本。
  采集无面板状态下 1/2/4 worker 的吞吐、内存和延迟分布，记录硬件与测量条件。
  2026-10-22 已完成 benchmark_sampling.py：9 轮、2,700 场、44,100 次决策，对应
  公开轨迹指纹一致，报告含硬件、计时范围与进程 RSS；异常/超时清理测试通过。
  复现验证需检查新环境安装步骤；2026-10-22 在同机全新检出目录重新下载依赖、
  构建并通过 46 项测试（1 项可选 PowerShell 跳过）；60 个固定用例公开轨迹与旧构建
  一致。证据为 artifacts/repro-check.json，仍不等于另一台机器已验证。
  本阶段验证训练接口，不开展 RL 学习，也不预先承诺吞吐或胜率。
P1-07 原版参考集验收（依赖 P1-03/04/05/06，当前 0/60）
  运行固定 3 遭遇 × 10 开发种子 × 2 策略的 60 条独立完整实机参考战斗。
  另补失败等边界探针；覆盖出牌/结束回合/跨回合/状态牌意图与入堆/能力/死亡/胜负。
  每条原版轨迹匹配独立模拟器重执行；缺失、未决、合成记录均不得计为通过。
  仅比较独立实测字段，规则表借来的牌面数值另行标注；不得作为原版测量证据。
  证据：acceptance 索引、完整捕获和哈希、重放报告、全部 case 与覆盖结果。
P1-08 第一阶段交付（依赖前述验收通过）
  交付一套可安装配置、操作说明、支持范围、来源说明、基准与有限一致性报告。
  每个里程碑提交可复核 commit；全部完成后再标记阶段版本，计划中不预设完成日期。
  GitHub 同步与 Windows 接入分别追踪；已提供仓库 URL 不等于服务器具备写入凭据。

当前首要执行单元
  用户：Windows 获取接入包，运行 Connect-Windows.ps1，保持 SSH 隧道。
  我们：核对报告、适配并编译桥接、给出安装步骤、完成一次读取/动作/确认的实机证据。
  并行可推进：P1-02 的适配器边界及 P1-06 的接口/复现证据，不能伪造实机验收通过。

第一阶段完成条件
全部适配器/协议/面板检查通过；60 条实机参考及边界覆盖完成；每一步可追溯。
游戏版本、规则源码、Mod、模拟器二进制或证据变化后，已有结论失效并重新核验。
结论应写“某版本、这些场景、这些字段通过参考集验证”，不扩大为全游戏完全一致。
界面可运行、模拟器自测通过或接口合成测试通过，单独都不足以完成第一阶段。

阶段 2：搜索与分层决策
  先实现带时间/节点预算的单场战斗搜索，使用玩家可见历史和未知状态采样。
  引入上层目标、战斗计划、原子动作三级记录，明确持续步数、终止条件和回退行为。
  路线、奖励、商店等整局动作需先扩展环境协议和原版参考用例，再用于层级实验。
  逐步验证单幕范围内的资源/牌组决策；每增加机制都补独立参考。
  持续推进自研有限引擎与最小桥接，保持来源说明和逐步切换，不继承旧引擎的证明。
  接入原版决策截图并与观测/动作绑定，Linux 模拟分支继续使用结构化展示。
  出口：策略与日志可重放；在保留种子、固定预算下完成随机/启发式/搜索/分层对比，
  包括关闭搜索、关闭层级、不同采样/预算的消融。报告置信区间与失败，不预设必然收益。
  只完成几场演示不能支撑优于基线的研究结论。

阶段 3：高效训练与原版评测
  自研采样调度、数据管理、搜索与学习衔接；模型计算使用通用框架。
  先建立可复现的学习基线，再比较策略/价值学习、模仿搜索结果与价值引导搜索。
  使用进程隔离采样、批量推理、检查点恢复与可追溯数据；保持原始事实和奖励版本。
  开发数据用于调参，保留集用于最终评测，按新场景继续划分数据防止评测泄漏。
  扩展到明确支持的整局内容，逐批做原版对照并测量模拟器到实机性能差距。
  交付带原版画面的自动对局和面板，记录帧时点、决策时点和执行确认。
  出口：可复现实验/模型/配置、独立评测、消融、采样量/墙钟时间/算力/内存/决策
  延迟报告；效率收益在相同硬件和任务条件下比较，研究结论仅覆盖已验证的范围。
